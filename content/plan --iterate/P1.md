## The Big Picture First

Before diving into tasks, it helps to see how everything connects:
```
Real-world Oil & Gas Docs
          ↓
  [Pre-processing Classifier]  ← PRIORITY BUILD
  (Quality tier routing)
          ↓
    ┌─────┴─────┐
  High        Low quality
  quality      → flagged, held
    ↓
  OCR via Gemini 2.5 Flash (Cloud Run)
          ↓
  EF Lookup → ef_master (BigQuery)
          ↓
    ┌─────┴──────┐
  Match        No match
  found        → Gemini estimates EF
    ↓                ↓
  Return EF     Medium confidence flag
  (no AI)
          ↓
  [correction_queue] ← bad EFs + bad OCRs land here
          ↓
  Human review via Review UI
          ↓
  Approved corrections → [correction_corpus]
          ↓
  (TBD) Fine-tuning pipeline on Vertex AI
```
Everything you build feeds into this flywheel — bad outputs get caught, corrected by humans, and eventually become training data.

## Phase 0 — Orientation (Week 1)

Before writing a single line of code, you need to understand the existing system deeply.

**What to do:**

- Get access to GCP, BigQuery, Cloud Run, Vertex AI, GitHub, ClickUp, MongoDB
- Audit the existing Cloud Run deployment — understand how documents flow in, how Gemini 2.5 Flash is called, and what the current output format looks like
- Inspect the `ef_master` table on BigQuery — understand its schema (columns, data types, how EF values are keyed, what the source citation field looks like)
- Run the existing pipeline on 10–20 real documents manually and note where it breaks
- Ask for a sample of documents that are known to be "bad" (poorly scanned, handwritten, non-standard templates)

**What you need:**

- BigQuery read access (at minimum) to `ef_master`
- Cloud Run service URL and any relevant API keys
- Sample document set (both good and bad quality)
- Existing codebase on GitHub cloned locally

**Output of this phase:** A written audit — what works, what breaks, and where the gaps are. This will directly inform your `correction_queue` schema and classifier design.

## Phase 1 — Review Gemini 2.5 Flash Output Quality

This is your observability and baselining task. You can't improve what you don't measure.

**What to do:**

- Define failure categories for OCR outputs:
    - Extraction failure (returned nothing or garbled text)
    - Partial extraction (missed tables, footnotes, units)
    - Wrong EF value mapped (extraction was fine but wrong field extracted)
    - Formatting failure (output structure doesn't match expected schema)
- Run a batch of real documents through the platform
- Tag each output with a failure category and severity
- Build a simple logging layer in Cloud Run that captures:
    - Input document metadata (filename, upload timestamp, doc type)
    - Gemini raw output
    - Confidence signal (if any)
    - Whether `ef_master` matched or AI fallback was used

**What you need:**

- A structured logging format (JSON to BigQuery or Cloud Logging)
- A spreadsheet or lightweight labelling tool to manually tag failures initially
- At least 50–100 real documents to get meaningful signal

**Output of this phase:** A failure taxonomy + baseline metrics (e.g., extraction failure rate, AI fallback rate). This directly informs what goes into `correction_queue`.

## Phase 2 — Maintain and Understand ef_master

This is ongoing but front-loaded. Understanding `ef_master` is a prerequisite for everything else.

**What to do:**

- Document the full schema — every column, what it means, and how it's populated
- Understand the matching logic — is it exact match? fuzzy? based on document type + activity + unit?
- Identify gaps — are there EF categories commonly requested but missing from the table?
- Set up a schema change process — any additions/modifications to `ef_master` should go through a PR-style review (version controlled, logged)
- Understand the source citation format — this matters for the review UI later

**Key questions to answer:**

- What is the primary key for `ef_master`? (e.g., activity type + unit + region?)
- How often does it get updated, and by whom?
- Is there a confidence or data quality column already, or does that need to be added?

**Output of this phase:** Full schema documentation + a clear understanding of when the AI fallback gets triggered (this defines your `correction_queue` input conditions).

## Phase 3 — PRIORITY: Pre-processing Document Quality Classifier

This is the most technically novel part of your role and the highest value add.

**The problem:** Gemini works fine on clean PDFs. It degrades significantly on low-DPI scans, handwritten text, and non-standard templates. You need a gate before Gemini sees the document.

**Architecture:**
```
Incoming document
       ↓
  Quality Classifier (Cloud Run)
       ↓
  ┌────┴────┬──────────┐
Tier 1    Tier 2    Tier 3
Clean     Moderate   Poor
  ↓          ↓         ↓
Direct    Preprocess  Flag &
to OCR    then OCR   hold for
                     human review
```

**What to do:**

_Step 1 — Define your quality tiers:_

- **Tier 1 (High):** Clear scan, typed text, standard template — send straight to Gemini
- **Tier 2 (Medium):** Some noise, slightly skewed, mixed fonts — apply image pre-processing (deskew, denoise, contrast boost) before Gemini
- **Tier 3 (Low):** Heavily degraded, fully handwritten, unreadable tables — flag immediately, route to `correction_queue` without running Gemini

_Step 2 — Build the classifier:_

- Start simple — a **lightweight vision model** or even heuristic-based rules (DPI check, blur score, text density via a quick pdfminer pass) can get you 80% of the way
- You can use **Vertex AI Model Garden** to deploy a small image classification model for this, or a custom model trained on your labelled samples
- Consider using Gemini itself for initial labelling of your training data ("Rate this document scan quality: High / Medium / Low") to bootstrap your classifier training set

_Step 3 — Pre-processing pipeline for Tier 2:_

- Tools: `OpenCV`, `Pillow`, `pypdf2`, `pdf2image`
- Operations: deskewing, denoising, contrast normalisation, resolution upscaling
- Deploy this as a pre-processing step in Cloud Run before the Gemini call

_Step 4 — Flagging logic:_

- Tier 3 docs get written to `correction_queue` with `status = "flagged_pre_ocr"` and `reason = "low_quality_input"`

**What you need:**

- A labelled sample of 200–500 documents across quality tiers (start manual, bootstrap with Gemini)
- Cloud Run service for the classifier (can be a separate service or a middleware layer in the existing one)
- Vertex AI for hosting the classifier model if you go beyond heuristics
- `OpenCV`, `pdf2image`, `Pillow` in your Python dependencies

**Output of this phase:** A quality-tiered routing layer that protects Gemini from inputs it can't handle well, reducing your bad OCR rate significantly.

## Phase 4 — correction_queue Table + Review UI

This is your human-in-the-loop infrastructure. Both bad EFs and bad OCRs land here.

**correction_queue Schema (proposed):**

| Column                 | Type          | Description                                    |
| ---------------------- | ------------- | ---------------------------------------------- |
| `id`                   | STRING (UUID) | Primary key                                    |
| `document_id`          | STRING        | Reference to source document                   |
| `queue_type`           | ENUM          | `bad_ocr` or `bad_ef`                          |
| `status`               | ENUM          | `pending`, `in_review`, `approved`, `rejected` |
| `original_output`      | JSON          | What the AI produced                           |
| `suggested_correction` | JSON          | Human-entered correction                       |
| `confidence_level`     | ENUM          | `low`, `medium`, `high`                        |
| `failure_reason`       | STRING        | From your failure taxonomy (Phase 1)           |
| `quality_tier`         | ENUM          | Tier 1/2/3 from classifier                     |
| `reviewer_id`          | STRING        | Who reviewed it                                |
| `created_at`           | TIMESTAMP     | When it was flagged                            |
| `resolved_at`          | TIMESTAMP     | When it was corrected                          |

**What gets written here and when:**

- Tier 3 doc from classifier → `queue_type = bad_ocr`, `status = pending`, before Gemini runs
- Gemini OCR fails or partial extraction detected → `queue_type = bad_ocr`, post-OCR
- AI fallback EF with medium confidence → `queue_type = bad_ef`, post-EF-lookup
- Reviewer manually flags something wrong → status update on existing record

**Review UI:**

- A simple web interface (can be a lightweight React or even a Streamlit app initially)
- Shows: document image side-by-side with extracted text + EF value
- Reviewer can: approve, reject, or correct the output
- On approval → writes to `correction_corpus`
- Stack: can live as a Cloud Run service, connecting directly to BigQuery

## Phase 5 — correction_corpus Table

This is your gold dataset — it grows over time and eventually powers finetuning.

**correction_corpus Schema (proposed):**

|Column|Type|Description|
|---|---|---|
|`id`|STRING (UUID)|Primary key|
|`source_queue_id`|STRING|FK to correction_queue|
|`document_id`|STRING|Source document|
|`corpus_type`|ENUM|`ocr_correction` or `ef_correction`|
|`input_image_gcs_path`|STRING|GCS path to document image|
|`original_ai_output`|JSON|What the model originally produced|
|`corrected_output`|JSON|Human-approved ground truth|
|`correction_notes`|STRING|Optional reviewer notes|
|`approved_by`|STRING|Reviewer ID|
|`approved_at`|TIMESTAMP|Timestamp|
|`used_in_finetune`|BOOLEAN|Flag for when it enters a training run|
|`finetune_run_id`|STRING|Which finetuning job used this record|

**Key design principle:** Every corrected record in `correction_corpus` is a future JSONL training example — the `input_image_gcs_path` + `corrected_output` pair maps directly to the multimodal SFT format you'll need in the TBD finetuning phase.
